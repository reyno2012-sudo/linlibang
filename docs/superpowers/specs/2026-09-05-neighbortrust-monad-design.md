# NeighborTrust：邻里帮 Monad 链上托管设计

日期：2026-09-05

## 1. 背景与目标

邻里帮现有产品已经具备社区互助、AI Agent 发单、候选人匹配、订单履约、信用风控和高风险服务安全规则。本次 Monad Blitz 的开发窗口有限，参赛版本不重写现有应用，而是在现有移动端与 Node.js 服务之外增加一层最小化的 Monad 智能合约。

参赛产品名称暂定为 **NeighborTrust — AI-Powered Local Service Escrow on Monad**。

产品主张是：AI Agent 负责理解真实世界需求、识别风险和匹配邻居；智能合约负责资金托管、履约状态和不可篡改的信用事件。目标是完成一条可现场演示的真实链上闭环，而不是加入与业务无关的代币或 NFT。

## 2. 范围

### 2.1 MVP 包含

- 连接浏览器钱包并检测 Monad 网络。
- 将 AI 整理后的任务发布为链上托管订单。
- 使用少量 Test MON 作为真实演示托管资金。
- 支持接单、提交完成、发布者验收付款和未接单退款。
- 监听并展示合约事件、交易状态、订单编号和交易哈希。
- 在个人资料中展示由链上完成事件计算的履约次数。
- 将任务隐私数据保留在现有前端或后端，仅将摘要哈希和必要状态写入链上。

### 2.2 MVP 不包含

- 平台代币、积分币或可交易 NFT。
- DAO 治理或完整的社区仲裁流程。
- 法币上链、人民币稳定币映射或真实支付结算。
- 主网部署、正式审计和生产级身份认证。
- 将姓名、详细住址、手机号、照片或儿童信息写入链上。

## 3. 系统架构

系统分为三个边界清晰的模块：

1. **现有移动端**：保留 AI 发单与社区交互；新增钱包连接、交易签名、链上状态与浏览器链接。
2. **现有 Node.js 后端**：保存隐私字段、AI 解析结果、风险判断和候选匹配；记录链上订单 ID 与业务订单 ID 的映射。
3. **Monad 智能合约**：保存订单摘要、参与钱包、托管金额和状态；执行权限检查、退款与付款；发出可索引事件。

链上状态是资金和履约状态的最终事实来源。后端与链上不一致时，客户端重新读取合约并修正本地展示。

## 4. 智能合约设计

合约暂定名为 `NeighborEscrow`。每个订单包含：

- `taskId`：递增链上订单编号。
- `taskHash`：业务任务规范化内容的哈希，不包含明文隐私。
- `requester`：发布者钱包。
- `helper`：接单者钱包，未接单时为空地址。
- `amount`：托管的 Test MON 数量。
- `status`：订单状态。
- `createdAt` 与 `completedAt`：必要时间戳。

状态机为：

```text
Open -> Accepted -> Completed -> Released
  |          |          |
  +----------+----------+-> Disputed
  |
  +-> Cancelled
```

比赛 MVP 暴露五个主要操作：

- `createTask(taskHash)`：可支付函数，创建订单并锁定 `msg.value`。
- `acceptTask(taskId)`：未参与订单的钱包接单。
- `markCompleted(taskId)`：仅接单者可调用，将订单置为待验收。
- `approveAndRelease(taskId)`：仅发布者可调用，先更新状态，再向接单者付款。
- `cancelTask(taskId)`：仅发布者可取消尚未接单的订单并退款。

如时间允许，增加 `raiseDispute(taskId)`，仅冻结资金并发出事件，不在比赛版内实现裁决。所有状态变化均发出事件，至少包括 `TaskCreated`、`TaskAccepted`、`TaskCompleted`、`FundsReleased`、`TaskCancelled` 和可选的 `TaskDisputed`。

安全约束包括角色权限、合法状态转换、禁止发布者自接单、先更新状态后外部转账、防重复结算、零金额与空哈希校验。合约不允许管理员任意提走用户托管资金。

## 5. 数据与隐私

AI 解析后生成一份规范化任务数据，包括服务类别、模糊位置、时间、现实报价、风险级别和安全规则。客户端对规范化数据进行确定性序列化并生成 `taskHash`，链上仅保存该哈希。

以下数据不上链：姓名、楼栋房号、手机号、聊天内容、证件材料、照片、儿童和老人相关信息。后端保存业务订单 ID 与链上 `taskId`、交易哈希和合约地址的映射。页面将“现实报价”和“链上演示托管”明确分开，例如“服务报酬 10 元”和“Demo 托管 0.01 Test MON”，不宣称 Test MON 等价于人民币。

## 6. 用户体验

### 6.1 钱包入口

首页顶部增加“连接钱包”。连接后显示缩略地址、Monad 网络状态和测试币余额。网络不正确时提供切换网络操作；未安装钱包时提供安装提示，同时允许用户继续浏览原有功能。

### 6.2 AI 任务卡

现有 AI 任务卡新增：现实报价、Test MON 托管金额、风险等级、上链字段说明和隐私字段说明。主要操作改为“发布并托管”。用户签名前可以再次检查所有字段。

### 6.3 交易反馈

交易进度按“等待钱包签名—等待链上确认—链上任务已创建”展示。成功后展示链上订单号、交易哈希和区块浏览器入口。用户拒绝签名或交易失败时保留草稿，并提供可理解的错误提示和重试入口。

### 6.4 订单与信用

订单页展示 `Open`、`Accepted`、`Completed`、`Released`、`Cancelled` 或 `Disputed` 的中文状态，并按当前钱包角色展示合法操作。个人资料页的“链上履约次数”由 `FundsReleased` 事件计算，不复用现有可编辑信用分冒充链上信用。

## 7. 端到端数据流

1. 居民输入自然语言需求。
2. AI Agent 解析任务、判断风险并生成候选匹配信息。
3. 用户确认现实报价与 Test MON 托管金额。
4. 客户端生成任务摘要哈希并请求钱包签名。
5. `createTask` 在 Monad 上创建订单并托管测试币。
6. 客户端读取交易回执，将链上订单 ID 与业务订单关联。
7. 另一钱包调用 `acceptTask` 接单。
8. 接单者调用 `markCompleted`。
9. 发布者调用 `approveAndRelease`，合约自动释放资金。
10. 页面读取 `FundsReleased` 事件，更新订单状态与链上履约次数。

## 8. 异常处理

- **钱包不存在**：给出安装提示，不破坏普通浏览和原有非链上功能。
- **错误网络**：阻止提交，提示切换 Monad 网络。
- **签名被拒绝**：恢复可提交状态，保留任务草稿。
- **测试币不足**：显示余额不足和 Faucet 引导。
- **交易待确认**：保持明确的 pending 状态，防止重复提交。
- **交易失败**：解析可识别错误，允许重试，不提前写入成功状态。
- **链上与本地不一致**：以合约读取结果为准，重新同步本地缓存。
- **现场网络不稳定**：准备一个已完成的测试网订单及浏览器链接，但正式演示仍优先走真实交易。

## 9. 测试与验收

### 9.1 合约测试

- 创建订单会锁定正确金额并发出事件。
- 非法角色不能接单、完成、验收或取消。
- 状态只能按允许路径推进。
- 未接单订单可退款，已接单订单不能直接取消。
- 已付款订单不能重复付款。
- 转账失败不会造成错误的最终状态。

### 9.2 前端与集成测试

- 钱包未安装、拒绝签名、错误网络和余额不足有明确反馈。
- 交易确认前按钮不可重复提交。
- 刷新页面后可从链上恢复订单状态。
- 区块浏览器链接指向真实合约或交易。
- 原有 AI 发单、社区内容、信用风控和后端测试继续通过。

### 9.3 Demo 验收

- 合约部署在 Monad 测试网并可公开查询。
- 两个测试钱包走通“创建—接单—完成—付款”。
- 页面展示真实交易哈希、链上订单 ID 和资金状态。
- 完成订单后，接单者的链上履约次数增加。
- 演示人员能在三分钟内讲清 AI、智能合约和 Monad 各自解决的问题。

## 10. 比赛叙事

NeighborTrust 解决的不是“把社区应用搬上链”，而是陌生邻居之间的小额、高频、本地服务缺少可信托管与可携带履约记录的问题。AI 降低发布和风险判断门槛，智能合约消除平台对资金结算的单方控制，Monad 的低延迟、高吞吐和并行执行适合大量独立社区微订单并发发生的场景。

演示重点是一条真实交易闭环。扩展愿景可以包括可验证凭证、跨社区信誉、保险和社区仲裁，但这些均不进入本次 MVP。
